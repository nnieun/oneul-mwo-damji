# 오늘 뭐 담지 — 구현 기획서

- 작성일: 2026-09-07
- 기준: 현재 프로젝트 소스와 첨부된 AI 비전 기반 스마트 마트카트 기획서
- 범위: 구현 계획 및 개발 규칙. 이 문서 작성으로 기능 구현·테스트 실행·커밋이 완료된 것은 아니다.

## 1. 목표와 기술 구성

카메라로 인식한 상품을 사용자가 확인하여 장바구니에 담고, 예상 구매금액과 보유 재료 기반 레시피를 확인하는 로컬 시연용 서비스를 구현한다.

| 항목 | 구현 방향 |
| --- | --- |
| 프론트엔드 | 기존 React·TypeScript·Vite·Tailwind CSS 유지 |
| 백엔드 | FastAPI |
| 데이터베이스 | SQLite |
| 카메라 | 백엔드에서 OpenCV로 연결 |
| 상품 인식 | Roboflow 학습 모델의 추론 결과 사용 |
| 프론트·백엔드 연결 | REST API 및 카메라 미리보기 스트림 |
| API 문서 | FastAPI OpenAPI 기반 Swagger UI |
| 테스트 | FastAPI 기능마다 pytest 작성·실행 필수 |
| 테스트 기록 | 기능별 별도 Markdown 파일 |
| 커밋 | 기능 구현·테스트·결과 기록·Swagger 반영 후 기능별 커밋 |

실제 결제, 회원가입, 재고 관리, 다중 카트 운영은 MVP에서 제외한다.

## 3. 전체 연결 구조

```text
백엔드 PC에 연결한 USB 웹캠
  → OpenCV 영상 읽기·프레임 준비
  → FastAPI에서 Roboflow 추론 요청
  → 모델 라벨을 SQLite 상품으로 매핑
  → React 인식 후보 표시
  → 사용자 확인
  → FastAPI 장바구니 저장·예상 금액 계산
  → 상품의 식재료와 레시피 비교
  → React 장바구니·총액·추천 갱신
```

기본 환경은 웹캠과 FastAPI가 같은 PC에서 실행되는 구성이다. 다른 기기의 브라우저에서 접속해도 사용하는 카메라는 백엔드 PC의 카메라다. OpenCV는 영상 입출력, Roboflow 모델은 상품 인식을 담당한다.

카메라 읽기는 백그라운드 작업 하나에서 수행하고 미리보기와 스캔이 최신 프레임을 공유한다. 초기에는 스캔 버튼을 눌러 추론하며, 추론 중 추가 요청을 제한한다. 카메라 종료와 서버 종료 시 자원을 해제한다.

## 4. 기능별 구현 계획

| 기능 | 동작 및 처리 기준 |
| --- | --- |
| 쇼핑 시작 | 활성 장바구니 조회, 없으면 생성 |
| 카메라 시작·종료 | 장치 연결 상태 확인 및 자원 해제 |
| 미리보기 | 백엔드가 읽은 영상을 React에 표시 |
| 상품 스캔 | 최신 프레임으로 추론 요청 |
| 후보 표시 | 상품명·가격·신뢰도·담기·제외·상품 변경 |
| 후보 확정 | 사용자 확인 후에만 장바구니 추가 |
| 상품 변경 | 등록 상품 목록에서 올바른 상품으로 수정하여 확정 |
| 수량 변경 | 서버에 최종 수량 전달, 응답으로 화면 갱신 |
| 삭제 | 항목 제거 후 총액·추천 갱신 |
| 복원 | 새로고침·서버 재시작 후 장바구니 조회 |
| 레시피 추천 | 장바구니 식재료와 필수 재료 비교 |

### 인식 및 중복 방지

- 초기 신뢰도 기준은 기존 코드의 0.75를 출발점으로 사용한다.
- 기준 미달은 재스캔을 안내한다. 기준 이상도 사용자 확인을 거친다.
- 미등록 라벨은 임의 상품으로 대체하지 않는다.
- 한 스캔에서 동일 상품은 최고 신뢰도 후보 하나로 표시한다.
- 영상에 계속 보인다는 이유만으로 수량을 자동 증가시키지 않는다.
- 후보에 `candidate_id`를 부여하고 한 번만 확정할 수 있게 한다.
- 동일 요청 키로 담기를 재전송해도 한 번만 반영한다.
- 같은 상품 추가 구매는 새 스캔 확인 또는 수량 버튼으로 처리한다.
- 후보의 확정·제외·만료 상태를 관리한다.

모델 ID·버전·접속 정보는 구현 시 설정한다. 접속 정보는 백엔드 환경변수에서만 관리한다. 실제 모델과 더미 추론 모드는 화면에서 명확히 구분한다.

## 5. SQLite 데이터 설계

| 테이블 | 주요 필드·역할 |
| --- | --- |
| products | 상품 ID, 판매명, 정수 원화 가격, 이미지 또는 이모지 |
| product_labels | 모델 버전·탐지 라벨과 상품 ID 매핑 |
| ingredients | 식재료 ID, 표준 식재료명 |
| product_ingredients | 상품과 식재료 연결 |
| carts | 장바구니 ID, 상태, 생성·수정 시각 |
| cart_items | 장바구니 ID, 상품 ID, 수량, 담을 때 단가 |
| recognition_candidates | 스캔 ID, 후보 ID, 상품, 신뢰도, 상태, 만료 시각 |
| recipes | 레시피 ID, 이름, 조리 시간, 인분, 조리 순서 |
| recipe_ingredients | 식재료, 필요량 표시, 필수 여부 |
| processed_requests | 중복 담기 방지 요청 키 및 처리 결과 |

- 가격은 원 단위 정수로 저장한다.
- 동일 장바구니의 동일 상품은 하나의 항목으로 합친다.
- 후보 확정과 장바구니 갱신은 하나의 트랜잭션으로 처리한다.
- 서버가 저장된 단가와 수량으로 금액을 계산한다.
- 식재료는 상품명 문자열 대신 공통 식재료 ID로 비교한다.
- 시드 재실행 시 중복 삽입하지 않는다.
- 기존 DB 변경은 버전이 있는 마이그레이션으로 관리한다.
- 테스트는 시연 DB와 분리된 임시 SQLite 파일을 사용한다.

기존 테스트의 공유 인메모리 연결은 실행 스레드와 충돌할 가능성이 있어 초기 단계에서 연결 수명과 테스트 DB 구성을 점검한다. 이는 코드 검토 사항이며 실행으로 확인한 오류는 아니다.

## 6. API와 Swagger 문서화

공식 API 문서는 FastAPI의 OpenAPI 자동 생성 기능을 사용하는 Swagger UI로 제공한다.

- Swagger UI: `http://localhost:4000/docs`
- OpenAPI JSON: `http://localhost:4000/openapi.json`
- 그룹: Health, Products, Camera, Recognition, Cart, Recipes
- 모든 API에 설명, 요청·응답 모델, 예시, 오류 응답을 작성한다.
- 기능 변경 시 Swagger 문서를 함께 갱신한다.

아래 목록은 목표 API 계약이며 아직 모두 구현된 경로는 아니다.

| 메서드 | 경로 | 역할 |
| --- | --- | --- |
| GET | /api/health | 서버 상태 |
| GET | /api/products | 상품 목록·검색 |
| POST | /api/camera/start | 카메라 시작 |
| POST | /api/camera/stop | 카메라 종료 |
| GET | /api/camera/status | 연결·오류 상태 |
| GET | /api/camera/stream | 미리보기 스트림 |
| POST | /api/recognition/scan | 최신 프레임 추론 및 후보 생성 |
| POST | /api/recognition/candidates | 기존 탐지 결과 변환 API 유지 |
| POST | /api/recognition/candidates/{candidate_id}/dismiss | 후보 제외 |
| POST | /api/carts | 장바구니 생성 |
| GET | /api/carts/active | 활성 장바구니 조회 |
| GET | /api/carts/{cart_id} | 항목·수량·소계·총액 |
| POST | /api/carts/{cart_id}/items | 후보 확인 또는 수동 상품 담기 |
| PATCH | /api/carts/{cart_id}/items/{product_id} | 최종 수량 변경 |
| DELETE | /api/carts/{cart_id}/items/{product_id} | 항목 삭제 |
| GET | /api/recipes | 레시피 목록 |
| GET | /api/recipes/{recipe_id} | 재료·조리 순서 |
| GET | /api/carts/{cart_id}/recommendations | 장바구니 기반 추천 |

기존 `/api/cart/items`와 `/api/cart/estimate`는 프론트 전환 후 폐기 여부를 결정한다. 전환 중 기존 API 의미를 조용히 변경하지 않고 Swagger에 구분한다.

| 대상 | 계약 |
| --- | --- |
| 후보 | candidate_id, product, confidence, 위치 정보, 상태 |
| 담기 요청 | product_id, quantity, 선택적 candidate_id, 중복 방지 요청 키 |
| 수량 변경 | 증감값 대신 quantity 최종값 |
| 장바구니 응답 | id, items, total, item_count, revision |
| 추천 응답 | 레시피 정보, matched, missing, optional_missing, 추천 분류 |

미존재 404, 처리·만료 후보 충돌 409, 입력 오류 422, 카메라 사용 불가 503, 모델 응답 시간 초과 504를 구분하고 예시를 문서화한다.

## 7. 프론트·백엔드 연동

- API 주소는 `VITE_API_BASE_URL`로 관리한다.
- 개발 포트는 기존 프론트 8443, 백엔드 4000을 기준으로 한다.
- 후보·상품 가격·장바구니·추천은 API 응답을 사용한다.
- API 신뢰도 0~1을 화면에서 0~100%로 변환한다.
- 변경 성공 후 서버 장바구니 응답을 표시하고 추천을 갱신한다.
- 연속 수량 변경은 순서대로 처리하고 오래된 응답의 화면 덮어쓰기를 방지한다.
- 실패 시 기존 장바구니를 유지하고 재시도를 안내한다.
- 연결 성공 전에는 카메라 활성으로 표시하지 않는다.
- 스캔 화면에도 예상 총액 요약 영역을 제공한다.

### 상세 데이터 예시

```json
{
  "id": 1,
  "name": "계란볶음밥",
  "cooking_time_minutes": 10,
  "servings": 1,
  "ingredients": [
    {"name": "계란", "amount": "2개", "required": true},
    {"name": "대파", "amount": "1/4대", "required": true},
    {"name": "밥", "amount": "1공기", "required": true},
    {"name": "간장", "amount": "1작은술", "required": true},
    {"name": "식용유", "amount": "1큰술", "required": true},
    {"name": "참기름", "amount": "약간", "required": false}
  ],
  "steps": [
    "대파를 잘게 썰고 계란을 풀어 둔다.",
    "팬에 식용유를 두르고 대파를 볶는다.",
    "계란을 넣고 저어 익힌다.",
    "밥과 간장을 넣고 골고루 볶는다.",
    "원하면 참기름을 넣어 마무리한다."
  ],
  "is_dummy": true
}
```

### 추천 규칙

1. 필수 재료가 모두 있으면 `재료 모두 보유`로 분류한다.
2. 필수 재료가 1~2종 부족하고 일치 재료가 있으면 `조금 더 담으면 가능`으로 분류한다.
3. 필수 재료가 3종 이상 부족하거나 일치 재료가 없으면 기본 추천에서 제외한다.
4. 선택 재료 부족은 분류에 영향을 주지 않고 별도 표시한다.
5. 부족 재료 수 오름차순 → 일치 비율 내림차순 → 조리 시간 → 레시피 ID 순으로 정렬한다.
6. 빈 장바구니에는 재료 추가 안내를 표시한다.

계란·대파·소금만 담았다면 파계란탕은 재료 모두 보유, 두부계란국은 두부 1종 추가 필요로 표시한다.

## 9. pytest·결과 MD·커밋 필수 규칙

> FastAPI 기능을 구현하거나 변경할 때마다 반드시 pytest 테스트 코드를 작성하고 실행한다. 실행한 테스트 결과는 기능별 별도 Markdown 파일에 기록한다. 기능 구현, 관련 테스트 통과, 결과 기록, Swagger 반영을 마친 후 기능 단위로 커밋한다.

| 기능 | 필수 검증 |
| --- | --- |
| DB·시드 | 초기화, 재실행 중복 방지, 제약조건, 연결 종료 |
| 상품 | 목록, 검색, 가격, 미등록 상품 |
| 카메라 | 연결 성공·실패, 프레임 읽기 실패, 반복 시작·종료, 자원 해제 |
| 모델 연결 | 정상 결과, 빈 결과, 시간 초과, 잘못된 응답 |
| 후보 | 신뢰도 경계, 미등록 라벨, 중복 제거, 제외·만료·재확정 |
| 장바구니 | 담기, 수량 변경, 삭제, 조회, 재시작 후 유지 |
| 중복 방지 | 같은 요청 재전송 시 한 번만 반영 |
| 금액 | 소계, 총액, 빈 장바구니, 미등록 상품 거부 |
| 추천 | 필수·선택 구분, 부족 재료, 정렬, 빈 장바구니 |
| Swagger | /docs, /openapi.json, 필수 경로·요청·응답 스키마 |

일반 pytest에서는 카메라와 Roboflow를 대체 객체로 검증한다. 실제 장치·모델 테스트는 별도 표시한다. 장비나 접속 정보가 없어 실행하지 못한 항목은 미실행 또는 SKIP으로 기록한다.

### 결과 파일 경로

```text
docs/test-results/F01-database.md
docs/test-results/F02-products.md
docs/test-results/F03-cart.md
docs/test-results/F04-camera.md
docs/test-results/F05-recognition.md
docs/test-results/F06-recipes.md
docs/test-results/F07-integration.md
```

각 결과 파일은 해당 테스트 실행 후 생성한다. 아직 실행하지 않은 결과 파일에 통과 기록을 미리 작성하지 않는다.

### 결과 문서 양식

```markdown
# F03 장바구니 테스트 결과

- 실행 일시:
- 실행 환경:
- 테스트 대상 코드: 기준 커밋과 변경 범위
- 실행 명령:
- 종료 코드:
- 결과: PASS / FAIL / SKIP / 미실행
- 집계: passed / failed / skipped
- 소요 시간:

## 검증 항목

| 항목 | 예상 결과 | 실제 결과 | 판정 |
| --- | --- | --- | --- |

## 실행 로그

## 실패 원인과 수정 내용

## 재실행 결과

## 남은 검증
```

실패 이력과 재실행 결과를 함께 남긴다. 기능별 커밋에는 기능 코드, pytest 코드, Swagger 관련 변경, 테스트 결과 MD를 함께 포함한다.

커밋 메시지 예시: `feat(cart): SQLite 장바구니 저장과 수량 관리 구현`

## 10. 구현 순서 및 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 실행 환경·기존 테스트 점검 | 기존 동작과 실패 원인 기록 |
| 2 | SQLite 구조·상품·레시피 시드 | 재실행해도 중복 없이 데이터 유지 |
| 3 | 장바구니·금액 API | 저장·조회·수정·삭제·중복 방지 검증 |
| 4 | 레시피 추천 API | 실제 보유·부족 재료와 분류 검증 |
| 5 | OpenCV 카메라 | 영상 표시, 오류 안내, 자원 해제 |
| 6 | Roboflow·후보 처리 | 실제 추론부터 확인 후 담기까지 연결 |
| 7 | React API 연동 | 기존 화면에서 전체 흐름 동작 |
| 8 | 통합 검증·시연 안내 | Swagger·pytest·결과 MD·기능별 커밋 완료 |

최종 시연 흐름:

```text
카메라 시작 → 상품 스캔 → 후보 확인 → 장바구니 저장
→ 총액 갱신 → 레시피 추천 → 수량 수정·삭제 → 새로고침 후 복원
```

실제 모델 성능은 별도 평가 데이터로 측정한다. 첨부 기획서의 mAP50 0.80은 초기 검토 목표로 유지한다. 더미 추론이나 pytest 통과를 실제 인식 성능 검증으로 대신하지 않는다.
