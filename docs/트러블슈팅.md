# 트러블슈팅

## 실제 스캔 결과가 "인식 후보"에 하나도 안 뜸 (2026-09-07)

### 증상

`DEMO_MODE=false`, `ROBOFLOW_MODEL_ID=sang-rqj4u/ozm-4-yolov8n-t1`로 전환하고 실제 카메라로 상품 스캔을 해도 "인식 후보"가 계속 0개로 나왔다. 브라우저 요청은 200 OK로 정상 처리됐다.

### 원인 파악

`RoboflowModel.infer()`에 임시로 `print`를 추가해 서버 로그에 Roboflow의 원본 응답을 남기고 실제로 스캔을 재현했다.

```
image_bytes=27716
predictions=[
  {class: 'sliced_ham', confidence: 0.1319, ...},
  {class: 'apple',      confidence: 0.0795, ...}
]
```

즉 모델은 실제로 정상 동작하고 있었다(요청·응답 파이프라인 문제 아님). 다만:

1. **신뢰도가 임계값에 한참 못 미쳤다.** `CONFIDENCE_THRESHOLD=0.75`인데 실측 신뢰도는 8~13%였다.
2. **더 근본적으로, 이 모델의 학습 클래스 10개(apple, bread, carrot, egg, galic, l_onion, onion, raw_pork, shrimp, sliced_ham) 중 상품 카탈로그(18종)에 실제로 존재하는 건 `egg`(계란)와 `onion`(양파) 2개뿐이었다.** 나머지 8개는 신뢰도가 아무리 높아도 매칭될 상품 자체가 없어서 후보가 될 수 없었다.

### 조치

모델이 인식하는 나머지 8개 품목(사과·식빵·당근·마늘·대파(l_onion 별칭)·돼지고기·새우·슬라이스 햄)을 상품 카탈로그에 추가했다([seed.py](../backend/app/seed.py)). 대파는 이미 있던 상품이라 새 상품을 만드는 대신 기존 `green_onion` 라벨에 `l_onion` 별칭을 추가로 매핑했다. 라벨 문자열은 모델이 실제로 반환하는 철자(`galic` 등 오탈자 포함)를 그대로 사용해 `ROBOFLOW_LABEL_MAP` 설정 없이도 기본 매핑이 되도록 했다.

카탈로그 시드는 스키마 버전 1에서 한 번만 실행되도록 되어 있어([db.py](../backend/app/db.py) `initialize()`), 이미 버전 1로 마이그레이션된 기존 DB에는 새 상품이 절대 반영되지 않는다. 스키마 버전을 2로 올리고, 버전 1인 기존 DB는 서버 재시작 시 `_seed()`를 한 번 더(멱등하게) 실행해 새 상품만 추가하도록 마이그레이션 경로를 넣었다. 기존 장바구니·상품 데이터는 그대로 보존된다.

### 진단에 사용한 방법

- Playwright에 `--use-fake-device-for-media-stream`을 줘서 실제 카메라 없이도 브라우저 캡처→업로드 파이프라인 자체가 동작하는지 먼저 검증(200 OK, 유효한 빈 `predictions` 확인 — 가짜 영상엔 실제 물체가 없으니 빈 결과가 정상).
- 그다음 실제 사용자가 진짜 카메라로 스캔하는 순간 서버 로그에 Roboflow 원본 응답을 남겨 실제 신뢰도·라벨을 확인. 원인을 찾은 뒤 임시 로그는 제거했다.

### 교훈

- "모델이 인식을 못 한다"는 증상은 (a) 연동 자체가 깨진 것, (b) 신뢰도 임계값 문제, (c) 카탈로그·라벨 매핑 누락이라는 서로 다른 원인일 수 있다. 원본 모델 응답(라벨+신뢰도)을 그대로 볼 수 있는 통로가 없으면 이 셋을 구분할 수 없다 — 그래서 `/api/recognition/scan` 응답에 매칭 여부와 무관하게 원본 `detections`를 항상 포함하도록 API를 바꿔뒀다(프론트 "모델 인식 결과" 섹션).
- 시드 데이터를 스키마 버전 1회성으로만 심는 구조에서 카탈로그를 확장하려면, 새 행을 추가하는 것만으로는 안 되고 스키마 버전을 올려 기존 DB에도 마이그레이션이 다시 타도록 해야 한다.

## 브라우저 카메라 화면이 검은 화면으로만 보임 (2026-09-07)

### 증상

실제 인식 모드(`DEMO_MODE=false`)로 전환하고 카메라 시작을 눌렀을 때, 상태 배지는 `실제 카메라 · 연결됨`으로 정상 표시되지만 미리보기 영역은 계속 검은 화면이었다. 브라우저의 카메라 권한 요청은 정상적으로 떴고 거부하지 않았다.

### 원인 1: `<video>` 태그에 크기 스타일이 없음

`index.css`의 카메라 미리보기 스타일이 기존 `<img>` 태그 기준으로만 작성되어 있었다.

```css
.camera-panel img { width: 100%; height: 100%; object-fit: contain; }
```

더미 모드에서는 `<img src=".../api/camera/stream">`로 미리보기를 그렸지만, 실제 모드로 전환하면서 브라우저 카메라를 직접 보여주기 위해 `<video>` 태그를 새로 썼는데 이 태그에는 크기 지정이 전혀 없었다. `<video>`는 기본적으로 크기를 지정하지 않으면 브라우저 기본 크기(약 300×150)로만 렌더링되어 카메라 패널을 채우지 못한다.

**조치**: `img`와 `video`에 동일한 크기 규칙을 적용했다.

```css
.camera-panel img, .camera-panel video { width: 100%; height: 100%; object-fit: cover; }
```

### 원인 2 (진짜 원인): `<video>`가 스트림 연결 시점에 아직 DOM에 없었음

CSS를 고친 뒤에도 화면은 여전히 검은색이었다. 원인은 JSX의 조건부 렌더링에 있었다.

```tsx
{camera.state === 'running' && config.mode === 'live'
  ? <video ref={videoRef} ... />
  : ...}
```

`<video>`는 `camera.state`가 `'running'`일 때만 화면에 나타나도록 되어 있었다. 그런데 카메라를 켜는 함수는 다음 순서로 동작했다.

```ts
const stream = await navigator.mediaDevices.getUserMedia(...)
if (videoRef.current) { videoRef.current.srcObject = stream; await videoRef.current.play() }
setCamera({ state: 'running', message: '카메라 연결됨' })   // 이 시점에야 <video>가 마운트됨
```

`getUserMedia`가 성공한 시점에는 아직 `camera.state`가 `'starting'`이라 `<video>`가 DOM에 없고, 따라서 `videoRef.current`는 항상 `null`이었다. `if (videoRef.current)` 조건이 조용히 실패하면서 스트림은 한 번도 실제로 연결되지 않은 채 `setCamera`만 `running`으로 바뀌어 배지는 "연결됨"으로 표시됐다. 이후 `running`이 되면서 `<video>`가 새로 마운트되지만, 이미 스트림을 연결하는 코드는 지나간 뒤라 빈 `<video>`만 남는다. 화면의 검은 박스는 실제 카메라 영상이 아니라 `.camera-panel`의 배경색(`#191f28`)이었다.

**조치**: `<video>`를 조건 없이 항상 마운트해두고, 보이기/숨기기만 `hidden` 속성으로 제어하도록 바꿨다. 이렇게 하면 `startCamera()`가 실행되는 시점에 `videoRef.current`가 이미 존재한다.

```tsx
<video ref={videoRef} autoPlay playsInline muted hidden={!(camera.state === 'running' && config.mode === 'live')} />
{camera.state === 'running' && config.mode === 'demo' && <div className="camera-placeholder">...더미 모드...</div>}
{camera.state !== 'running' && <div className="camera-placeholder">...{camera.message}</div>}
```

### 검증

Playwright에 `--use-fake-device-for-media-stream` 플래그를 주고 실제 카메라 없이 헤드리스로 재현했다. 카메라 시작 후 `<video>` 엘리먼트를 캔버스에 그려 픽셀 평균 밝기를 확인한 결과, 수정 전에는 원인 파악 목적으로는 확인하지 않았지만 수정 후 `readyState: 4`(재생 가능), `paused: false`, 평균 밝기 54(0이 아님)로 실제 프레임이 들어오는 것을 확인했다.

### 교훈

- 스트림/리소스를 `ref`에 연결하는 코드는 그 `ref`를 가진 엘리먼트가 **이미 마운트되어 있다는 보장이 있는 곳**에서만 실행해야 한다. 마운트 여부를 상태(`state`)로 제어하면서 그 상태를 만드는 비동기 작업 안에서 같은 `ref`를 참조하면, 마운트 시점과 참조 시점이 어긋나는 경쟁 상태(race condition)가 생기기 쉽다.
- `if (ref.current) { ... }`처럼 조용히 실패하는 가드는 디버깅을 어렵게 만든다. 이번 경우 실패해도 예외가 나지 않고 상태만 "연결됨"으로 바뀌어서, 겉으로는 정상 동작처럼 보였다.
- UI 요소를 표시/숨김만 하고 싶을 때는 마운트/언마운트(조건부 렌더링)보다 `hidden` 속성이나 CSS로 제어하는 편이, DOM 참조를 다루는 코드와의 타이밍 문제를 피하는 데 더 안전하다.

## 참고: 더미 모드 → 실제 모드 전환

같은 세션에서 `backend/.env`의 `DEMO_MODE=true`를 `false`로 바꾸고 `ROBOFLOW_MODEL_ID`, `ROBOFLOW_API_KEY`를 채운 뒤 백엔드 프로세스를 재시작해야 했다. `.env`는 서버 시작 시 한 번만 읽으므로(`uvicorn --env-file .env`, reload 미사용), 값만 바꾸고 서버를 재시작하지 않으면 프론트가 계속 더미 모드로 보인다.
